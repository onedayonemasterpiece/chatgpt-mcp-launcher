# Ревьюер по расписанию + окна ChatGPT: проверенная схема

24.10.2026. Опыт роли **RKB-Продукт** (Claude Code, Opus) за ~30 часов работы в проекте Regional Knowledge Base. Это продуктовый ревьюер, который каждые 30–45 минут сам просыпается, читает координационный Slack-тред и PR, принимает продуктовые решения и сам запускает исполнителей — окна ChatGPT через этот Launcher.

Документ — вход для проектирования такой же схемы на **Codex + окна ChatGPT**. Ниже то, что сработало, механика и ошибки, которые повторять нельзя. Конкретные пути и имена взяты из RKB как пример.

---

## 1. Роль: одна зона, явные полномочия, одна метрика

- **Одна зона ответственности** и одна главная метрика. Пример: «первая книга целиком находится поиском; тёплый p95 поиска ≤1000 мс; страниц/ч». Отдельные ревьюеры для соседних зон: RKB-Opus — сложность кода и merge, RKB-Истории — качество историй, RKB-Гео, RKB-Ответы. Каждый — своё окно со своим расписанием.
- **Полномочия записаны явно.**
  - Формат вето: `<Роль> VETO PR#N: причина → что сделать`, одинаково в тред и комментарием в PR.
  - Снятие: `<Роль>: вето PR#N снято`.
  - Чего роль НЕ делает: не сливает, не пушит код, не трогает live, не ревьюит построчно.
- **Каждое действие проверяется по трём вопросам:** приближает ли цель? нет ли нового этапа, барьера, гейта или связки несвязанных функций? не добавляет ли синхронный шаг на критический путь?
- **Владельца ведут на уровне продукта.** Ему не дают выбирать PR, SHA или формулировки прав. Ему никогда не выдают «выполни команду». Его просьба уже является разрешением — не ждать отдельного «да».

## 2. Механика расписания (Claude Code)

- **Цепочка одноразовых задач** вместо recurring, если нужен ровный интервал. Recurring-задача сдвигается планировщиком на случайное смещение до 50% периода, поэтому интервалы плывут. Каждый проход в конце сам ставит следующий: `date -d "+45 min" "+%M %H %d %m"` → одноразовая задача с этим cron.
- **Страховочная recurring-задача** раз в 3 часа. Она проверяет список задач: если одноразового прохода нет, то есть цепочка оборвалась, — выполняет проход сама.
- **Промпт цикла — в файле, а не в теле задачи.** Задача содержит одну строку «прочитай и выполни инструкцию из файла …». Так инструкцию можно менять между проходами: решение владельца сразу попадает в следующий проход.
- **Всё постоянное — не в `/tmp`.** Промпт, состояние (`state.json`) и helper лежат в постоянной папке. На devserver это `/home/dev/artifacts/<project>/<task>/` через `dev-artifacts new --retain`. Перезагрузка хоста дважды стёрла `/tmp` вместе с состоянием.
- **Задачи живут только в сессии.** После перезапуска сессии или хоста цикл восстанавливается из файлов: проверить список задач → пересоздать цепочку и страховку.
- **Частота — по смыслу.** Днём 30 минут. Ночью и при экономии — 45 минут, по решению владельца. Тихий проход, когда нового нет, ничего не пишет и только обновляет состояние.

## 3. Структура одного прохода

1. **Читать только новое.**
   - Курсор `last_ts` — это время последнего полного чтения, а не ts своего сообщения: иначе пропускаются чужие.
   - Свои сообщения отфильтровывать.
   - Большой вывод Slack сохраняется в файл и разбирается python-ом. Сначала короткие выдержки по всем сообщениям, полный текст — только нужных.
2. **Свой факт, а не пересказ.** Один обычный пользовательский вызов продукта (здесь — `search`): статус, данные, латентность. Это ловит «всё зелёное, а продукт лежит».
3. **PR, обновлённые с прошлого прохода:** размер +/−, черновик или нет, CI. На критическом пути — смотреть, что именно добавляется.
4. **Исполнители:** по каждой открытой задаче — кто делает и есть ли STARTED. Смотреть в `~/.local/state/chatgpt-launcher/queue.json` (jobs, chats, `model_status`, `model_summary`).
5. **Решение:** вето или поддержка, назначение исполнителя, запуск окна, эскалация.
6. **Сообщения:**
   - **В тред** — только то, что меняет действия агентов.
   - **Владельцу** — 3–6 строк. Первая строка всегда про общее состояние продукта: работает ли, метрика, что изменилось к готовности. Отчёт не сводится к одному текущему блокеру.
7. **Обновить `state.json` и поставить следующий проход.**

Что хранить в `state.json`:
- `thread_last_ts`, номер прохода;
- просмотренные PR и их HEAD;
- решения с исполнителем и статусом STARTED;
- запущенные job_id;
- метрики;
- активные вето;
- очередь «после разморозки».

## 4. Исполнители: решение без исполнителя — не прогресс

- **Принятое решение — ещё не прогресс.** На следующем проходе проверить: назван ли исполнитель и есть ли STARTED. Если нет — назначить сразу. Не докладывать «в плане»: ночная ошибка — идея пролежала полдня с пометкой «в плане».
- **Ревьюер страхует координатора.** Координатор (dot) — основной, но он встаёт на первой ошибке. Если пункт без исполнителя, завис или брошен на хвосте — ревьюер сам запускает или продолжает окно в том же проходе, без лишнего прохода «на решение».
- **Держать 3–5 окон загруженными.** Было «0 активных окон при полной очереди» — это главный ночной провал. Считать активные окна каждый проход. Субагенты координатора — тоже ресурс.
- **Но не загружать фичами, пока ядро нестабильно** (см. §6).
- **Тесты организует ревьюер.** Тестовый участник, отдельный тестовый тред, отдельное окно-тестировщик. Не ждать «привязки к профилю владельца». Пример: тест Slack-бота полдня ждал «да» владельца, хотя годился любой тестовый эксперт.

### Как звать Launcher из агента

- **Вызов:** loopback MCP — JSON-RPC `tools/call` POST на `http://127.0.0.1:8177/mcp`.
- **Заголовок:** `Authorization: ` + содержимое `~/.config/chatgpt-launcher/mcp-authorization.header` (файл уже начинается с `Bearer …`). Читать в helper-скрипте, **никогда не печатать** даже частично. Однажды `head -c` вывел префикс токена в лог агента — такой токен надо ротировать.
- **Инструменты:**
  - `chatgpt_start`, `chatgpt_continue{chat_ref}`;
  - `chatgpt_task_status`;
  - `chatgpt_reconcile` — для `needs_review`;
  - `chatgpt_retry` — для `blocked` с промптом, оставшимся в поле;
  - `chatgpt_list_chats`.
- **Правила:**
  - Стабильный `request_id`: повтор не создаёт дубль.
  - Перед запуском проверить `queue.json`: нет ли уже окна на эту задачу.
  - Свободное окно — последний job `done` и `continuation_count < 5`. Шестой continue сам откроет новый чат.
  - «Prompt already on its way» означает, что координатор уже отправил туда задачу: не дублировать.
  - `blocked` с нашим промптом в поле — доказанно не доставлен, повтор безопасен.
- **Ожидание доставки:** `Monitor`/цикл с `until` до `sent`, затем `model_status=started`.

### Что всегда в промпте окна

- Ссылка на координационный тред — все видят сообщения друг друга.
- Роли: кто единственный сливает (merge), кто единственный трогает live, кто единственный пишет в этот участок (например, «импорт книги ведёт один исполнитель»).
- Точная задача, файлы и места, критерий приёмки и чего НЕ делать.
- Формат отчёта: сразу `STARTED` → `DONE` с PR/HEAD/CI, либо `blocked` с точным вопросом и адресатом.
- Если окно продолжает чужую работу — «тот же PR, та же ветка, новой реализации не нужно».

## 5. Эскалация: длинный простой — гипотеза переусложнения

- **Правило:** если критический шаг (запуск, READY, «страница → видна в поиске») лежит больше часа или падает второй раз — не докладывать статус, а выдвинуть гипотезу «система переусложнена».
  - Самому посмотреть падающий гейт: файл и строку.
  - Найти, какой существующий механизм уже покрывает ту же гарантию.
  - Передать владельцу зоны сложности в тот же проход.
- **Пример, полночи «поиск ещё не поднят».** Каждый перезапуск упирался в новое «доказательство поверх fencing»:
  - лимит снимка;
  - replay хвоста до READY;
  - fingerprint 12 файлов;
  - terminal-proof с обязательным непустым логом и PIN версии SDK;
  - ручной список маршрутов в history verifier.
  Единственного писателя уже держала одна защита (writer generation и retired reservation). Ни одна из этих проверок не ловила реальный сбой, все лишь блокировали запуск.
- **Своё окно-аудит в чужую зону не запускать.** Сложность — зона кодового ревьюера (RKB-Opus). Найти, назвать, передать.
- **Метрика вместо статуса при нестабильности:** аптайм продукта за 3 часа и единицы работы в час (страниц/ч).

## 6. Анти-паттерны, за которые уже заплатили

1. **Gate creep.** «Сначала X, потом основной поток» — новые условия перед главным потоком копятся, и time-to-market уходит в бесконечность. Улучшения — пока поток идёт.
2. **Фичи параллельно нестабильному ядру.** Пять окон на каталог, GEO и бота, пока поиск падал. Каталог сломал совместимость и был откатан, GEO полез в файлы запуска. Правило: **заморозка** — до N часов стабильности в main не идут фичи, все окна только на вычитание.
3. **Давить на скорость в обход ревью сложности.** «Не задерживай ради идеала» → PR слит под давлением → первый же live-вызов сломал → revert → продукт снова лёг.
4. **Заплатка поверх заплатки.** Один класс дефекта — «чужое незавершённое состояние держит основной поток» — чинили четырьмя PR. Нужно было одно общее правило.
5. **Статус-петля.** Однообразные отчёты «ещё не поднялось» без гипотезы.
6. **Узкое место из одного исполнителя.** Live-оператор одновременно и импортирует, и чинит, и пишет код. Live оставлять одному, код и импорт раздавать другим.
7. **Дубли.** Два окна на одну задачу в одну секунду — в том числе от самого ревьюера. Перед запуском проверить очередь и тред.
8. **«Все заняты» без перечня.** Принимать только «кто чем занят прямо сейчас».
9. **Ожидание подтверждения владельца** на работу, которую он сам поручил.
10. **Фича вместо критерия.** «Истории для туризма» — это критерий качества существующего текста, а не новая версия для соцсетей.

Правило для любого PR на критическом пути: **условий и строк становится меньше**. Новое условие — только с одной строкой «от какого реального сбоя». Хорошо работающий приём: попросить у кодового ревьюера список ≤10 условий на удаление и раздать по одному исполнителю на пункт. За час ушло ~420 строк лишних проверок.

## 7. Общение

- **В тред** — коротко, с ролью в начале (`RKB-Продукт:`), только меняющее действия. Не повторять других. Свои ошибки признавать одной строкой и сразу исправлять: «дубль ETA создал я, не dot».
- **Владельцу** — на его языке, 3–6 строк. Сначала общая картина: что работает, что нет, сколько времени до ценности. Без PR, SHA и команд. На вопрос «где мы относительно готовности» — честная сводка «работает / не работает / оценка», без оптимизма.
- **Вопросы владельца — признак пробела в работе.** Это сигнал закрыть пробел, а не повод написать длинный ответ.
- **Память агента:** каждое исправление владельца — отдельная запись (правило + почему + как применять). Тогда оно не повторится в следующей сессии.

## 8. Безопасность

- Секреты только из файлов, в helper, без вывода. Loopback MCP Launcher не выставлять наружу.
- Временные и диагностические файлы — в управляемый artifacts-каталог, с причиной хранения. Не в репозиторий и не в `/tmp` для того, что должно пережить перезагрузку. За сутки один проект набрал гигабайты брошенных worktree и тестовых выгрузок, и диск заполнился. Чистить за собой.
- Live трогает только назначенный оператор. Ревьюер — только чтение и обычные пользовательские вызовы.

## 9. Шаблон промпта ревьюера (скелет)

```
Ты — <Роль>: <зона> проекта <P>. Отвечаешь владельцу по-русски, кратко, по продукту.
ЦЕЛЬ И МЕТРИКА: <одна цель>, <числовые пороги>.
ЗОНА: <что проверяешь, 5–10 пунктов>. НЕ ЗОНА: <чужие роли>.
ПРОХОД раз в <N> мин (цепочка одноразовых задач + страховка раз в 3 ч; промпт в файле <path>; состояние <path>/state.json):
 (1) только новое в треде и PR; свой обычный вызов продукта;
 (2) по каждому: приближает ли цель, нет ли нового гейта/этапа/связки, нет ли синхронного шага на критическом пути;
 (3) исполнители: решение без STARTED за проход → назначь или запусти окно сам (Launcher helper, проверка дублей, стабильный request_id);
 (4) критический шаг лежит >1 ч или падает второй раз → гипотеза переусложнения, найди гейт и передай владельцу сложности;
 (5) при нестабильном ядре — заморозка фич, окна только на вычитание;
 (6) тред — только меняющее действия; владельцу 3–6 строк, первая — общее состояние.
ПОЛНОМОЧИЯ: VETO-формат, снятие. ЗАПРЕТЫ: merge, push, live, секреты, новые сервисы и гейты.
КООРДИНАЦИЯ: тред <ссылка>; роли <список>.
НАЧНИ: представься в треде одной строкой, сделай первый проход, запусти цикл.
```

## 10. Что решить для Codex + окна ChatGPT

Вопросы для нового окна. Здесь ответов нет: в Claude Code они решены встроенными средствами.

1. **Расписание.** Чем в Codex заменить цепочку одноразовых задач и страховку: systemd user timer, automation DevCoveer, свой cron, вызывающий `codex exec`? Нужен ровный интервал, перезапуск после перезагрузки и запрет параллельного запуска двух проходов.
2. **Контекст между проходами.** У Claude Code одна длинная сессия, у Codex каждый проход, вероятно, новый. Значит, `state.json` и короткая память роли — единственный носитель контекста. Что в них должно быть, чтобы проход не перечитывал историю?
3. **Доступ к Slack и Launcher из Codex.** Тот же loopback MCP Launcher; Slack — через имеющийся MCP или интеграцию. Без новых сервисов и без owner-токенов, по `devserver-interservice`.
4. **Экономия.** Тихий проход должен стоить почти ноль: сначала дешёвая проверка «есть ли новое» (ts треда, `updatedAt` PR, `queue.json`), и только при наличии нового — полный проход.
5. **Несколько ревьюеров** (Продукт, Истории, Гео, Ответы) на одном Launcher: как не запускать окна наперегонки — общий журнал назначений или правило «перед запуском проверить queue.json и тред».
